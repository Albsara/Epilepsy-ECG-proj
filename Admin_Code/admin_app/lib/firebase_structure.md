# Seizure Model Admin App - Firebase Architecture

This document maps out the comprehensive structure of the backend architecture utilizing Firebase. The system seamlessly integrates **Firebase Authentication**, **Cloud Firestore**, and **Firebase Realtime Database** to provide low-latency live telemetry alongside scalable historical record keeping.

---

## 1. Firebase Authentication
The platform uses standard Email/Password authentication for all users. 
To unify the data relationships without duplication, every Authentication `UID` generated uniquely maps exactly 1:1 to the user's primary document ID in Firestore.

* Primary Admin uses Firebase Auth to login originally.
* We employ a secondary Firebase Authentication instance under the hood when admins create new user accounts, guaranteeing that the active Admin session is never prematurely logged out.

---

## 2. Cloud Firestore (Primary Database)
Firestore acts as our primary persistence layer for relations, profiles, and immutable history logs.

### A. Many-to-Many Relationship Model
We have migrated to a root-level mapping system rather than nested subcollections for Users. A clean Array structure maintains relationships bidirectionally.

#### Collection: `patients`
Stores all patient personal details.
* **Document ID**: Matches the Patient's Firebase Auth UID.
* **Fields**:
  * `name` (String)
  * `email` (String)
  * `phone` (String)
  * `birthdate` (Timestamp)
  * `details` (String) - Associated medical notes.
  * `authUid` (String) 
  * `caregiverIds` (Array of Strings) - Maps precisely to the caregivers tasked to monitor this patient.
  * `createdAt` (Timestamp)
  * `updatedAt` (Timestamp)

#### Subcollection: `alerts` (Under `patients/{patientId}`)
Contains atomic historical logs automatically generated whenever a seizure flag occurs. We use a **Collection Group Query** (`collectionGroup('alerts')`) to extract and analyze every single alert globally for the Dashboard and Alerts History tabs.
* **Document ID**: Auto-generated by Firestore.
* **Fields**:
  * `heartRate` (Number)
  * `hrv` (Number) - Heart Rate Variability.
  * `time` (Timestamp) - The exact instant the seizure was triggered.
  * `isResolved` (Boolean) - True if the Admin marked the alert as handled.
  * `createdAt` (Timestamp)

#### Collection: `caregivers`
Stores details of doctors, nurses, and family members.
* **Document ID**: Matches the Caregiver's Firebase Auth UID.
* **Fields**:
  * `name` (String)
  * `email` (String)
  * `phone` (String)
  * `authUid` (String)
  * `patientIds` (Array of Strings) - Automatically maintains bidirectional reference to their assigned patients.
  * `createdAt` (Timestamp)
  * `updatedAt` (Timestamp)

---

## 3. Firebase Realtime Database (RTDB)
Because Cloud Firestore charges for "Document Reads", fetching live continuous heart-rate streams at 1-second intervals would be heavily inefficient and expensive. We utilize Firebase RTDB specifically for temporary, fast-paced IoT streaming.

#### Node: `live`
Maintains the absolute latest state variables published directly by IoT devices / Smartwatches.
* **Path**: `live/{patientId}`
* **Fields**:
  * `hr` (Int) - Live Heart Rate BPM.
  * `hrv` (Int) - Heart Rate Variability.
  * `medication` (String)
  * `symptoms` (String)
  * `sleep` (String) - enum mapped locally (e.g., 'good' / 'bad').
  * `stress` (String)
  * `updatedAt` (ServerValue.timestamp)

*Notice: Historical metrics and alerts are moved out of RTDB into Firestore via subcollections, ensuring RTDB remains lightweight and exclusively holds live statuses.*
